# BM25

BM25 (**Best Matching 25**) is the standard scoring algorithm behind lexical/keyword full-text search — the ranking function that decides how relevant a document is to a query based on the actual words it contains, as opposed to [vector search](vector-database.md)'s semantic/embedding-based similarity. It's what runs under the keyword half of [hybrid search](hybrid-search.md), and it's the engine behind most "full-text search" features you'd otherwise take for granted: [Elasticsearch](../../databases/search/elasticsearch.md), [OpenSearch](../../databases/search/opensearch.md), [Solr](../../databases/search/solr.md), and [Azure AI Search](../../cloud/azure/azure-ai-search.md) all use BM25 (or a close variant) as their default text-relevance scorer.

## What problem it solves

A naive approach to "how relevant is this document to this query" is to count how many times the query's words appear in it — more occurrences, more relevant. That breaks in two obvious ways:

- **Repetition doesn't scale linearly.** A document that says "leave policy" ten times isn't necessarily ten times more about leave policy than one that says it once — relevance saturates.
- **Long documents have an unfair advantage.** A 10,000-word document has far more chances to contain a query word by coincidence than a 200-word one, so raw term counts favor length over actual relevance.

BM25 builds on the older **[TF-IDF](tf-idf.md)** ([term frequency–inverse document frequency](tf-idf.md)) idea and fixes both problems with two explicit tuning parameters.

## The formula

For a query with terms `q1, q2, ..., qn`, a document `D`'s BM25 score is:

```
score(D, Q) = Σ IDF(qi) · f(qi, D) · (k1 + 1)
              ─────────────────────────────────
              f(qi, D) + k1 · (1 - b + b · |D| / avgdl)
```

| Symbol     | Meaning                                                                                                                                                |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `f(qi, D)` | How many times term `qi` appears in document `D`                                                                                                       |
| `\|D\|`    | Length of document `D` (word count)                                                                                                                    |
| `avgdl`    | Average document length across the whole corpus                                                                                                        |
| `k1`       | **Term-frequency saturation** — controls how quickly additional occurrences of a term stop adding relevance. Typical default: `1.2`–`2.0`              |
| `b`        | **Length normalization** — how much to penalize documents for being longer than average. `0` = no penalty, `1` = full penalty. Typical default: `0.75` |
| `IDF(qi)`  | **[Inverse document frequency](idf.md)** — how rare the term is across the corpus; near-zero for common words, large for rare ones                     |

See [IDF](idf.md) for the full formula, a worked example, and why it's the reason BM25 doesn't strictly need [stopword removal](analyzer-pipeline/stopword-removal.md) to behave reasonably.

## Why this matters more than the formula itself

Two design choices fall directly out of the math above, and they're the two things worth actually remembering for an interview or a design discussion:

1. **Term-frequency saturation (`k1`)** means BM25 rewards a document *containing* the query terms, not a document that *repeats* them — it resists simple keyword-stuffing.
2. **Length normalization (`b`)** means a short, focused document that mentions the query term once can outrank a long document that mentions it the same number of times — length alone isn't relevance.

## Why BM25 pairs with vector search instead of replacing it

BM25 is exact-match lexical scoring — it has no notion of meaning. It excels exactly where [embeddings](../ingestion/embeddings.md) tend to struggle: product codes, ticket numbers, legal clause references, proper nouns, acronyms — terms that [embeddings](../ingestion/embeddings.md) often blur into "something generically similar" rather than matching exactly. Vector search excels at paraphrasing and synonyms, which BM25 can't see at all (a query for "spending plan" scores zero against a document that only says "budget"). Running both and merging the results — typically via **[Reciprocal Rank Fusion (RRF)](reciprocal-rank-fusion.md)** rather than trying to directly compare BM25 scores against cosine similarity scores — is the standard [hybrid search](hybrid-search.md) pattern.

## Where it shows up in this handbook

- [Hybrid Search](hybrid-search.md) — the general pattern that combines BM25 with vector search
- [Azure AI Search](../../cloud/azure/azure-ai-search.md) — uses BM25 as its full-text scorer, combined with vector search and an optional semantic [re-ranker](cross-encoder-reranking.md)
- [PostgreSQL](../../databases/relational/postgresql.md) — Postgres's built-in full-text search (`tsvector`/`ts_rank`) is a different ranking function, not BM25 natively; reaching for actual BM25 semantics in Postgres means an extension (e.g. `pg_search`/ParadeDB) rather than the built-in `ts_rank`
